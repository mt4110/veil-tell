# トンネルの送信量

CONNECT 先ごとにクライアントから上流へ書き込んだバイト数、接続数、1接続の最大送信量を記録する。TLS の暗号文とハンドシェイクを含む。TLS 終端や URL・本文の解析は行わない。

基準には接続できたトンネルの計測値を保存する。既定のしきい値は同じバックエンドで取得した基準の8倍で、下限は合計 256 KiB、接続数 64、1接続 128 KiB。過去の計測値がない宛先に推測の上限は適用しない。既存の基準は引き続き読み込める。基準の追加承認で、既存の宛先のしきい値が上がることはない。キャッシュとコマンドの条件をそろえて採取する。配布やアップロードのように送信量が違う仕事は、専用の明示的な基準を使う。

`observe --baseline` は通知のみ。`ci` は基準から得た上限を実行中に適用し、`restrict` は許可ルールに `max_sent_bytes = 8192` のように指定すると実行ごとの合計を制限する。実際に転送する前に予算を検査し、同じ宛先への並行接続で共有する。上限を超える次の書き込みでトンネルを閉じるため、上限までのデータは受信側に届き得る。停止を JSON の `volume_anomalies` に記録して終了コード 22 を返す。未知の CONNECT が同じ実行で拒否された場合は従来の 20 または 21 を優先する。複数の送信元が同じ宛先を使った場合、帰属は調査候補の集合になる。

少量ずつ別の実行で送る、複数の許可済み宛先へ分ける、タイミングに情報を載せるといった通信は残る。HTTP/2 のストリームや TLS 内の用途は区別できない。集計はネットワーク上の機密性や悪性を示す指標ではない。

## インストールを基準にした受信側の比較

macOS 27.2 と Ubuntu 26.04.1 の両方で、同じローカル受信口を使って `npm install` の `postinstall` を比較した。採取時は 4,096 バイト。以降は同じ宛先に 524,288 バイトを送ろうとした。受信口はテスト用の名前解決を使う fixture で、製品バイナリがローカル宛先を許可する挙動とは異なる。

| 実行 | 受信したバイト数（両 OS） | veil-tell の終了コードと JSON |
| --- | ---: | --- |
| `observe --baseline-out` で通常の install を採取 | 4,096 | `0` |
| `observe --baseline` | 524,288 | `21`、`volume_anomaly`、`blocked: false` |
| `ci --baseline` | 131,072 | `22`、`volume_limit_exceeded`、`blocked: true` |
| `restrict`（ルールの `max_sent_bytes = 8192`） | 8,192 | `22`、`volume_limit_exceeded`、`blocked: true` |

全ケースで子の npm は `0`。異常の3ケースで JSON に `veil-volume-fixture@1.2.3 postinstall` の推定帰属が残った。受信バイト数は JSON の `destinations[].sent_bytes` と一致した。通常の npm install / ci を5回繰り返した対照は、両 OS で異常なし。

基準なしの observe は送受信比で警告しない。公開処理や API への書き込みでは、正常でも送信が受信を大きく上回る。標準の自動比較から npm / Cargo の `publish` は外し、明示的に基準を指定した観測と、ルールの上限を持つ制限実行を提供する。送信量は CONNECT トンネルの暗号化されたバイト数で、同じ宛先への少量ずつの送信や実行をまたぐ累計はこの比較の範囲外。
