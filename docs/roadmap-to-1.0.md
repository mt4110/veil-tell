## 0. 最終形、変えない原則、絶対優先軸

### 0.1 最終形（ゴール）
依存と AI エージェントが外に何を送ろうとしたかを、sudo なしで見張る番人。**置いたら忘れていられる状態**を目指す。

- 普段は黙っている。
- 鳴るのは「新しい送り先」「止めた試み」「いつもと違う送信量」の 3 つのときだけ。
- 鳴るときは、どのパッケージ・スクリプト・エージェントの操作かを添える。

ゴールは「全部止める」ことではない。**「静かで、鳴ったら必ず見る価値がある」**こと。

### 0.2 変えない原則
- **sudo 不要**: eBPF・カーネル拡張・pf/iptables の変更・システム拡張は使わない。
- **TLS は終端しない**: 中身は読まない。判断材料はホスト名・ポート・時刻・バイト数・回数・帰属だけ。
- **テレメトリー無送信**: veil-tell 自体は外に情報を送らない。共有するときは、利用者が自分の意思で公開する形に限る。
- **既定値で動く**: オプションなしの既定値でうまく動くようにし、細かい設定は上級者向けに残す。
- **誇張しない**: 「完全に防ぐ」とは書かない。止められないことは毎版明記する（[§10](#10-やらないこと止められないこと10の先)）。

### 0.3 絶対優先軸（設計・実装・判定の最上位基準）
仕様や実装で迷ったときは、必ず次の 2 つを最優先で満たす選択を取る。

1. **セキュリティに効きやすい（検知漏れ・偽陰性・すり抜け・誤認を防ぐ）**
   - **未観測や失敗を「静かな成功」に見せない**: 隔離失敗、基準不在、記録上限超過（`incomplete_capture`）、JSON 欠落は必ず失敗・未観測として明示し、黙って `exit 0` にしない。
   - **「止めた試み」を逃さず鳴らす**: 新規宛先だけでなく、明示拒否（`deny`）された既知宛先や直接通信拒否（`direct_attempts`）、記録できた名前解決試行も要約・通知に出し、攻撃の前兆を見落とさない。
   - **信頼境界と来歴を崩さない**: PR の検査では基準と lockfile を必ず信頼済み base SHA から読み（PR 側の変更で許可を緩めさせない）、同一バージョンの `integrity` 変更やライフサイクル帰属を強調する。バイナリの来歴検証（`gh attestation verify`）と採取・比較間の版一致を徹底する。
   - **判定理由を混同しない**: 子自身の終了コード（例: 子が独自に `21` で終了）を `veil-tell` の新規宛先 `21` と混同しない。
2. **ユーザーに使われやすい（導入障壁ゼロ・壊さない・迷わない）**
   - **既存環境を絶対に壊さない（0.5.x 最優先）**: 通常→隔離→通常で作業フォルダ・ロック・キャッシュ・外部 store の整合を保つ。
   - **静かなときは 1 行、鳴ったときも迷わない**: 正常な CI 要約は 1 行で終わらせる。鳴ったときは先頭に 1 行ハイライト（何が・どう止まり・誰のせいか・転送量）と「次の一手（確認・承認・保留の判断手順）」を出し、詳細表は下にまとめる。
   - **導入はコピペ＋手動 1 回で終わる（0.6）**: Actions テンプレートは主要マネージャー（npm / pnpm / Yarn / Bun / Cargo）で手順を揃え、前提不足（非 setuid `bwrap` の有無など）は失敗時に理由と対処を 1 行で案内する。

## 1. 誰が、いつ、何を判断できれば完成か

依存更新 PR を開いた保守者は、普段は通常の CI の結果を見るだけでよい。ある更新で初めて `storage.googleapis.com:443` に向かったら、その PR で宛先、拒否の有無、転送した量、判明したパッケージと根拠を一緒に読める。手元でエージェントを使う人は、セッションが終わった後でも、どの子コマンドでその事象が起きたかを追える。確認した変更だけを基準へ反映できる。これを、対応する環境で、日々の実行に sudo を使わず提供する。

**1.0 の完了条件**は、(1) 公称対応の各マネージャーで既存プロジェクトを引き続き使える、(2) テンプレートを実際の依存更新に1か月適用し、通知・誤報・欠測を分母付きで公開する、(3) Linux の対応条件と macOS で取得できる事実を実測表で示す、(4) エージェント経由の実行を根拠の強さとともに追える、(5) 公開形式と終了判定を旧データ・旧利用側を含む試験で固定し、配布物を利用側から検証する、の五つ。途中の版は、それぞれの範囲が先に完成したときに出せる。予定のタグ名はリリース承認と別に扱う。

### 1.1 番人が鳴る条件

CI ジョブの要約・ローカル履歴に共通の判定を置く。通常の計測、子コマンド自身の出力、ジョブの成否、任意の PR コメントはそれぞれ別の出力先である。「黙る」は、比較が成立し下表の事象がゼロなら利用者に対応を求めないこと。正常な CI 要約は1行でよい。観測不能時はチェックの失敗または制約を明示する。

| 鳴る理由 | 判定に使う事実 | 宛先と表示 | 受け入れ例 |
| --- | --- | --- | --- |
| 新しい宛先 | レビュー済みの基準との差。CONNECT は正規化 host＋port、名前解決の新規試行は名前で比較 | 観測点、初出、接続・拒否の結果。基準のない初回は候補採取 | 既知だけは静か。新規 CONNECT と新規の名前解決試行を区別できる |
| 止めた試み | ポリシー・CI・名前解決受付・直接通信監視等が、その試みを拒否した裏付けを持つ | CONNECT、質問名、IP:port を採れた形で表示。上流接続失敗や子自身の失敗は拒否として数えない | 明示拒否済みの既知宛先も要約で識別できる。直接試行を表示するには対応する coverage が必要 |
| いつもと違う送信量 | 同じ backend の基準サンプルまたは明示ルールの予算と比較 | 宛先ごとに実際の上流向きバイト数・接続数・最大1接続量と上限、観測か切断かを表示 | 上限内、ちょうど上限、超過する次の書き込み、同時接続、上流プロキシ経由を対照 |

想定する CI 要約の1行は「新規・拒否 ｜ storage.googleapis.com:443 ｜ puppeteer の postinstall（推定）｜ 転送 0 B」。帰属が不明ならその欄を「特定できず」とする。詳細を開くと、判断に使った基準と該当する report の行を追える。

一つの事象に複数の理由が付く。例えば初出かつ拒否なら1行に二つの理由を載せる。1実行の要約は1件、理由別の件数は重複可。同じ観測点・宛先・決定の再試行は回数として残す。DNS の質問と後続の CONNECT を時刻だけで同一通信にまとめない。消えた宛先、CONNECT 回数の変動、lockfile 差分、帰属候補の変更は調査材料。通知の判定でパッケージ名や推定エージェント名を許可根拠にしない。

「何を送ろうとしたか」について約束するのは、観測した宛先・種類・結果・帰属候補・トンネルの転送量まで。TLS の中身、URL のパス、拒否前に送る予定だった本文・総量は分からない。許可した接続も失敗し得る。受信 0 と未計測は区別する。量の初期値は既存の同一 backend の基準の 8 倍、下限は合計 256 KiB・64 接続・1接続 128 KiB。基準値のない宛先に量の異常を推定しない。[送信量の仕様と受信側実測](volume-limits.md)

## 3. 0.5.x の互換性を回帰試験にする

対応表の単位は OS・arch、マネージャー・版、lock 形式、コマンド、ホーム・キャッシュ・store の設定。基準環境は公開版の CI 定義に合わせた macOS arm64、Ubuntu x86_64 と aarch64。ローカル実機、VM、ホスト型 CI の証拠は区別する。初期の基準版は CI に記載された npm 11、pnpm 9/10/12、Yarn 1/4、Bun 1。Cargo は実行時に `cargo -V` と rustc の版を採る。版を上げる際は変更したセルを再測する。[CI の厳密な版と起動方法](../.github/workflows/test.yml)

| マネージャー | 凍結した入力で行う操作 | 固有の観察点 |
| --- | --- | --- |
| npm | `npm ci`、package-lock v2/v3 | 既存成果物の再利用、prefix 設定、ライフサイクルの推定、必要時はプロジェクト用ホームで導入後の実行まで |
| pnpm | `pnpm install --frozen-lockfile`、pnpm-lock v9 | 外側と内側の実効 store が同じ。未設定・別 store・cold Corepack を区別し、事前失敗で従来の依存を引き続き呼べる |
| Yarn Classic / Berry | Classic は `yarn install --frozen-lockfile`、Berry は `yarn install --immutable` | node_modules と PnP を対象の設定で検証。Berry の cache checksum と tarball の SRI はそれぞれの形式で解釈 |
| Bun | `bun install --frozen-lockfile`、対応するテキスト版 bun.lock | 信頼された fixture の lifecycle と lock の実内容。推定根拠がない帰属は unknown。旧バイナリ lock を対応扱いしない |
| Cargo | `cargo build --locked`、Cargo.lock v3/v4 | build.rs の候補、ワークスペース member、.crate の checksum、既存のビルド成果物が次の通常ビルドで使えるか |

P01/P02 は利用者の実ディレクトリのコピーまたは一時 fixture から、同じ初期状態の通常実行群と隔離実行群を作る。(1) 通常導入した依存と成果物で代表コマンドが動くか確認、(2) 冷・温キャッシュを分けて実行、(3) 同じ凍結 lock でもう一度通常実行、(4) 実際に依存を読み込み、必要な実行ファイルを起動する。CLI 本来の正常な install によるファイル更新は通常実行群を基準とし、lock・設定・意図せぬ置換・外部 store・成果物の所在を比較する。事前検査で拒否するケースは、子の未起動マーカー、既存ツリーと設定の前後ダイジェスト、旧依存の実行成功をセットで残す。失敗した install の途中変更全般を自動復元する約束にはしない。

レジストリ配布物に由来する検証には、版と期待 digest を固定した再配布可能な fixture と、各マネージャーが生成したロックを使う。正常・同一版で digest が異なる・欠落・複数版・形式外を作り分ける。表現できる証拠は lock の比較までである。lock 証拠を取れない場合も、観測済みの宛先と子の失敗理由は保存する。以前の pnpm の事前拒否、Corepack、ダウンロードした成果物の再利用、`accept` の復帰、shim stdin の挙動は既存試験を拡張する。[マネージャー試験](../tests/package_managers.py) · [ロックの読み取り](../src/lockfile.rs) · [導入と復旧](runbook.md)

## 4. 0.6 の Actions テンプレート

### 4.1 採取・レビュー・比較・復帰

1. 信頼済み base の手動実行で、固定した版の配布物の来歴を検証する。隔離内で §3 のコマンドを実行し、正常完了した基準候補と report を作る。既存 npm 例の手動採取は v0.4.0、PR は `@v0` を参照するずれがあった。A01 では採取側と PR 比較側が同一リリース（`v0.6.0` / `@v0`）に解決するよう揃え、Action の完全なコミット SHA、実行したバイナリの版・SHA-256 を記録する。浮動タグの更新は検査時点の参照先を残す。
2. メンテナーが候補の宛先と初期予算をレビューして、対応する基準を base にコミットする。PR ジョブは base SHA の基準と lock を読み、PR の作業ツリーを検査する。head に許可を追加してもその PR の判定は変わらない。baseline と比較の OS、ランタイム、マネージャー、コマンド、作業ディレクトリ、cache profile を一致させる。異なるときは差を表示し、再採取はレビュー経由とする。
3. report の構造化データから §1 の理由集合を1か所で計算し、ローカル要約・Actions 要約・運用集計で同じケース表を使う。既存 Action の要約は `comparison.added`、`attempted_added`、`volume_anomalies` のみ見ていたため、A01 では **比較外の明示拒否（`destinations[].decision == "deny"` やポリシー/CI 拒否）および裏付けのある直接拒否（`direct_attempts`）も「止めた試み」として漏れなく表示**する。また、ユーザーが一目で判断できるよう、鳴ったときは **1 行ハイライト（理由・宛先・帰属・転送量）と次の一手** を先頭に出し、詳細表と基準情報を下に添える。Linux の IP:port を新しい基準キーや第4の終了条件に昇格させない。
4. 新規宛先は保留・更新の取り下げ・独立に確認後の承認から人が選ぶ。承認後はクリーンな状態で再比較する。明示的な基準を渡した CI の report と、プロジェクト基準で作られるローカルの pending は別の成果物。CI の失敗を受けて PR の基準を自動更新しない。[基準の運用](destination-diff.md) · [現行 Action の base 取得](../action.yml)

### 4.2 配布するテンプレートと受け入れ

`examples/github-actions/` に npm、pnpm、Yarn Classic、Yarn Berry、Bun、Cargo の利用例をそろえる。各例に手動採取・必要なツールの固定と隔離内からの可視性・PR 比較・失敗時の案内が必要。Node を用意する既存 Action だけでは pnpm/Bun/Cargo の実行環境はそろわない。Yarn は lock のファイル名が両系で同じなのでプロジェクトが指定した版と設定からテンプレートを選ぶ。サブディレクトリ型のプロジェクトは、現在の root 相対 lock の扱いを検査し、対象に含めるなら base/head 両方の lock・作業ディレクトリ・baseline path を一緒に解決する。未検証の配置をコピー可能な例に含めない。

既定の PR は読み取り権限、checkout の資格情報の永続化なし、対象に秘密を渡さない設定とする。ジョブ定義・比較器・候補を信頼済み側で管理する。候補版から PR のコードへ書き込み権限を渡す方法で要約を改善しない。通常の通知面は job summary、PR コメントは明示 opt-in。現行のコメント条件は数値 `21` のため、子自身が返した `21` を新規宛先と誤る余地がある。A01 では要約器（および出力フラグ）側で report の `run_status.reason` と差分（`comparison.added` / `attempted_added` 等）を確認し、子失敗だけならコメント 0 件とする。既存の `pr-comment` は新規宛先用という約束を維持する。公開テンプレートが使う標準ランナー名と、実測した OS build/arch の両方を残す。

Ubuntu の既存例には bwrap がない場合に sudo でインストールする準備ステップがある。「sudo 不要」の受け入れは、非 setuid bwrap と user namespace のあるランナー上で、採取・比較・終了まで一般ユーザーで走ること。配布例は前提（`/usr/bin/bwrap` 実行可否と user namespace）を検査して不足を 1 行で説明し、管理者によるランナーの事前準備（`sudo apt-get install -y bubblewrap` 等）は分けて案内する。CI の隔離不成立は検査不能。ローカル短縮形のフォールバックと混同しない。[既存の例](../examples/github-actions/veil-tell-npm.yml) · [隔離の条件](../README.md#隔離の動作条件)

**A01/A02 の受け入れ表**

| 固定するケース | まとめとジョブに現れる結果 |
| --- | --- |
| レビュー済み宛先だけ・子成功・比較成立 | 要対応0件、終了 0、PR コメントなし。外部宛先が消えただけでも新規通知なし |
| 未登録 CONNECT／記録可能な新しい DNS 試行 | 隔離 CI で 21 と理由。名前、観測点、拒否、帰属候補または unknown が分かる |
| 既知名の拒否のみ・同じ IP の直接拒否を複数回 | 止めた事実と回数が1行。根拠のある経路だけ表示し、既存の終了コードを維持 |
| 観測比較で量が異常／実際に量上限で切断 | 既存の observe は 21、CI の切断は 22。理由、実測値、上限、受信側カウンタを照合 |

| head 側だけが基準を変更、同じ PR を再実行、基準をレビュー後に再実行 | base で拒否、再実行の集計が重複しない、レビュー後の新しい base では期待どおり復帰 |
| マネージャーの版・lock の種類・ランナーの前提が違う | 理由と直す場所が分かる。別版で基準を黙って採り直さない |

## 5. 1か月運用の設計

**問いは「実際の更新を何件見て、何回鳴り、うち何回は対応する必要がなかったか」。** npm の過去事例がある筆者リポジトリ（`image-drop-input` や `prompt-recipe` 等）を最初の候補とし、Cargo・veil-* 系の既存事例を次の候補とする。対象リポジトリ、パス、マネージャー、開始日、PR の選び方を開始前に記録する。候補に新しい workflow を置くこと、公開集計を外部に掲載することは、実行時に対象を指定して承認を受ける。誤報がほぼゼロかつ実運用データがそろった段階で記事等の公開判断に進む。[npm 実 PR の記録](runbook.md#image-drop-input-の依存更新-pr-76-での実測) · [従来の利用仮説](design.md#手軽さと需要を確かめる)

### 5.1 観測の単位

- 本設計での1か月は、レビュー済みジョブ有効化後の連続30日間 `[t0, t0 + 30日)`、時刻は UTC。初期対象についてこの期間中に依存ファイルの変更を初めて観測した自然な更新 PR を登録し、対象にした head SHA を記録する。開始前から開いていた PR は期間中の対象更新を境に含める。途中導入したマネージャーは別の開始日・日数を明記する。
- 対象 PR は workflow 実行履歴と独立に、対象リポジトリの PR と変更ファイルから列挙する。lock だけの更新を含める。paths 漏れ、ジョブの無効化、キャンセル、タイムアウト、report 欠落、読み取り不能も行を残す。運用中の設定変更（基準、cache profile、ランナーを含む）・停止日は区間を分け、窓から差し引いて見かけの成功を作らない。
- 実行の識別は `repo, PR, base_sha, pr_head_sha, checkout_sha, job/matrix, run_id, run_attempt`。checkout_sha は実行時の HEAD。標準の pull_request checkout は PR のマージ結果になり得るため、同じ head で base だけ進んだ再実行を区別する。[GitHub の PR checkout 仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#how-the-merge-branch-affects-your-workflow)
- 通知回数の単位は、発見事項を job summary へ表示できたジョブ実行。PR コメントなど別の表示先の件数は別列。総数に含まれる再実行分を別列で示す。「鳴った PR」は `repo, PR` で1件とし、期間中のどの対象実行で鳴ったかを残す。後の成功でも初回の通知を消さない。同じ PR の複数信号・複数環境を PR 数へ加算しない。
- 無害な陽性・陰性の対照、訓練用 PR、手動再生、スケジュールの疎通確認はそれぞれ別集計。対象 PR が無い日の対照成功は自然な依存更新の件数に入れない。窓内に発生した対象の base/head と必要ジョブを一覧にし、集計の締切を窓の終了時刻とする。締切時点で進行中なら保留、締切後の完了・再実行は追跡欄に記し、初版の数字を動かさない。外部保守者3人を対象にした従来の導入仮説は別の調査に属する。

### 5.2 判定と公開表

各実行で集計用に持つのは ID、版と条件、基準のダイジェスト、時刻、比較/coverage/終了理由、三理由の有無、比較可能な範囲、判定者・根拠へのローカル参照。事象を裏づける report と、利用者に表示した要約の成否を別欄にする。要約の書き込み結果とジョブ上の表示を照合し、通知あり・通知なし・表示不能・表示未確認を区別する。原文ログ、自由記述の argv・cwd、DNS 名、私的なホスト名を公開台帳へ自動転載しない。継続的なテレメトリー送信は不要。公開する例のドメインとリンクはメンテナーが確認する。

集計の単位ごとに「確認できた事象」と「比較できた範囲」を独立に保持する。途中までに明確な拒否が1件あり、その後で中断した実行なら、**記録できた拒否は1、静かだったと評価できる実行は0。表示に失敗すれば実通知は0、表示が確認できなければ実通知数は未確認**。PR の「全件評価可」は、締切までに窓内のすべての対象更新と事前指定したジョブについて評価可能な run がそろった場合。初回 head の全ジョブ成功後に別の対象 head が未起動なら「一部評価可」。対象の全ジョブが欠けていれば「全件欠測」。単なる `exit 0` や空配列は正常の証明に使えない。

| レビュー分類 | 判例と計数 |
| --- | --- |
| 要対応・正しい通知 | 正当な変更でも、新 CDN の追加を人がレビューする必要があった。真の新規宛先として数える |
| 観測は正しいが運用では不要 | キャッシュ条件の不一致等で繰り返し鳴り、依存更新に対処を要しなかった。不要通知として別掲 |
| 観測または分類が誤り | 子自身の 21 を新規宛先として通知する等。確認済み誤報として数える |
| 未判定 | 証拠不足・レビュー待ち。分母と未判定件数を示す |
| 静か／見逃し | 評価可能・無通知。独立した受信記録等で該当事象を確認できた場合だけ見逃し。正否未確認の無通知は陰性認定しない |

公開表はリポジトリ・マネージャー別に、期間、対象 PR、実行あり、全件/一部評価可、全件欠測、鳴った PR、実通知数と再実行分、三理由別件数、確認済み誤報、不要通知、未判定を載せる。技術的な誤報数と、運用者にとって余分だった数を混ぜない。正誤はまず各実行の表示行と理由ごとに判定する。正当な理由と誤報が同居すれば両方を保持し、実行・PR の「誤報を含む」はそれぞれ1件とする。警告理由中の誤報割合の分母は判定済みの表示理由数。未判定の理由・実行・PR は各粒度で別掲する。偽陽性率を載せるなら独立に陰性と判定した母集団が必要。分母 0 は「算出不可」。実更新が 0 件なら30日経過と件数をそのまま報告し、運用上の有効性の判定は保留。別窓で延長するか対象を追加して観測する。

**集計の受け入れ例（架空）**。自然な更新が3 PR。A は新規かつ拒否で鳴り、同じ head の再実行でも1回鳴った。B は比較成立・無通知。C は未起動。別途合成 PR が1件あった。期待値は対象3、実行あり2、全件評価可2、全件欠測1、鳴った PR 1、通知実行2（再実行1）、新規があった PR 1、拒否があった PR 1。A の妥当性がすべて未レビューなら、未判定 PR は1、未判定の通知実行は2、未判定の表示理由は4。技術的誤報割合は算出不可。運用担当は公開予定の表を、この入力から再計算できることを M01 の終了条件にする。追加対照として「JSON に拒否1、要約生成失敗」は記録1・表示不能1・実通知0、「同じ head で base のみ変更」は異なる検査対象、「締切後に未起動ジョブを再実行」は初版の欠測を維持、と照合する。

## 6. 0.7 で取得できる名前を増やす

### 6.1 観測経路と Linux の成立条件

```text
子の HTTPS CONNECT → 既存のローカル中継 → ホスト側のポリシー・上流接続
子の Node lookup   → 既存のフック       → 名前を記録して ENOTFOUND
子の標準 DNS       → 隔離内の受付       → 名前を記録して NXDOMAIN（段階 B の提案）
子の IP 直接試行   → 既存の OS 隔離     → 対応 Linux では IP:port を記録（段階 A）
```

段階 A はシステムリゾルバの接続先が `127.0.0.1:53` だったことを記録できる。ここで接続を止めると後続の DNS 質問はまだ送られていない。Ubuntu 26.04.1 の既定 AppArmor と bwrap 0.11.1 では隔離内 UDP/53 の bind が EACCES、高位ポートでの合成試験では NXDOMAIN、ホスト側模擬受信は対照1・隔離0だった。高位ポートを指定した専用クライアントの成功だけでは、標準リゾルバの経路は成立しない。[実験記録](../experiments/dns-attempts/README.md) · [DNS の現行仕様](dns-attempts.md) · [段階 A の処理](../src/linux_notify.rs)

**D01 の判断手順**。候補の Linux で、非 setuid bwrap、UID、カーネル、ユーザー名前空間・LSM の実効条件を記録する。隔離内の信頼する中継が使えるポートを子の起動前に確かめ、実際の標準リゾルバがそこに到達するかを測る。第一候補は専用 netns の loopback:53 で UDP/TCP とも bind できる既定構成。隔離専用 resolv.conf は読み取り専用で渡し、利用するアドレスファミリーを明記する。段階 A の既存の一律 :53 拒否との調整は、受付の準備を確認できた内部の正確な宛先に限って設計する。ホストの DNS・別の loopback サービス・外部上流へ接続する経路を増やさない。導入先の sudo・capability 追加・LSM 緩和を成立条件にしない。既定の Ubuntu で不成立ならそれ自体を対応表に残す。

**D01 の実測記録と代替方式（2026-11-21、先行実験ブランチ確認済み）**。Ubuntu x86_64 と Debian aarch64 の双方で、新しい netns における一般ユーザーの UDP/TCP 53 bind は拒否され、独立受信機でも隔離時は A/AAAA 各 0 件・前後対照各 1 件だったため、53 番 bind 前提の段階 B は両環境で保留となった。一方、**glibc NSS に届く名前解決要求**は 53 番を開かずに非特権で名前を記録できること（`nss_attempts`）が Python と配布版 curl で確認されており、実用性と sudo 不要原則の両面から Linux 向け拡張の有力な柱とする。ただし glibc NSS を通らない静的バイナリ（pure Go リゾルバ等）は記録できないため、**未観測経路を安全側に倒して明示（`not_observed` と対照表）し、取れる範囲を誇張しない**方針を貫く。

**D02 の利用側インターフェース案**。Linux isolated のセンサー選択を off（段階 A まで）、auto（受付を準備できた場合に観測）、required（受付必須）の3状態にする。別に「段階 B を比較するか」を選ぶ。比較を有効にするときは required とレビュー済みの B 用基準を要求する。基準の指定があるのに coverage が異なる場合は子起動前に 125。旧コマンドの比較条件は維持する。実装箇所は [Linux の中継と起動](../src/linux.rs)、[既存の Node hook](../src/node_dns.cjs)、[記録の回収](../src/lib.rs)。D01 の実験後に公開 CLI の綴りと既定のセンサー選択を決める。

**D02 の寿命とデータ**。監督側が受付作成→bind→正常応答の自己確認→子を1回起動→記録の回収→終了処理の順で所有する。自己確認の質問名と予算を子用集計から除外し、子の開始時は記録・予算消費ともゼロとする。DNS を一切使わない子で質問数0を確かめる。受付は質問の正規名と回数を記録し、許可した形式の質問にはローカルの否定応答を返す。ホストのリゾルバを呼ばず、再帰・転送・キャッシュ共有は行わない。UDP と長さ付き TCP、A/AAAA、大小文字・末尾ドット、重複問い合わせ、切断、不正な長さ・圧縮参照を試す。通常の対応条件は標準リゾルバを通した試験で決める。[DNS メッセージ形式](https://www.rfc-editor.org/rfc/rfc1035.html) · [DNS over TCP](https://www.rfc-editor.org/rfc/rfc7766.html)

- 受付の入力はサイズ、同時 TCP 接続、読み取り時間、名前の数、試行総数を有限にする。正規名は既存の `normalize_host` と比較し、扱えない質問は分類して件数のみ。DNS パケット、TXT 内容、クエリ全体のバイト列をログに残さない。名前自体にも機密情報を含み得るのでローカル保存と共有を区別する。既存の名前上限253バイト、異なる名前1,024、合計16,384を引き継ぐ。D01 の成果に、追加するバッファ・同時接続・タイムアウトの具体値、境界値±1の期待応答と資源解放を含め、D02 実装前に固定する。
- report では Node hook とシステム受付の観測範囲を識別する。提案は **追加の report 専用の観測元別集計**を用い、同じ質問を二重計数しないこと。既存の `attempted`・基準 v1 の厳格な行形式は維持し、問い合わせの種類や取得元をそこへ直接足さない。IP リテラル、採れなかった名前、難読な入力にホスト名を補わない。
- センサーの拡張だけで既存 CI が新規宛先として大量に失敗しないよう、段階 B による**比較**は明示選択。初回は旧比較を維持したまま別に候補を提示し、同一経路で採取した基準をレビューしてから有効化する。提案では新しい比較範囲を識別する場合は独立した版の基準を併用し、異なる取得元の履歴を黙って合算しない。ベース名・選択規則・writer/reader は C01 の fixture に追加する。
- 受付準備不能で B 任意なら「未対応＋理由」、厳密に B を要求するジョブでは子起動前に 125。開始後に受付が停止、記録が欠落、または上限を超える次の記録を保持できなければ対象 run の coverage を不完全とし、完了集計・基準更新を停止して 125。未観測を空配列の成功に変えない。起動済みか不明・起動後障害で子を再実行しない。センサーがなくても既存のネットワーク隔離は必要。

### 6.2 OS 別の合否表

各試行に固有の合成名を用い、ホスト側の独立した模擬受信機で「対照到達→隔離→再対照到達」を確認する。Case ごとに入力、戻り値、ローカル受付の件数、比較結果、外側受信数、OS build/arch と backend を対応付ける。外側0件の解釈には、隔離の前後とも同じ API・同じリゾルバ選択での対照成功が必要。高位ポートへ直接送る合成 UDP を、標準 API の対照には使わない。対照を作れない行は未確認。

| 経路 | Linux で確認すること | macOS で確認すること |
| --- | --- | --- |
| 既存 CONNECT／対応する Node lookup | CONNECT の成否・量と、hook に届いた名前。B 有効時も既存ルールを保つ | 同じ2経路を別々に検証。proxy-only と isolated を分けて表示 |
| libc、curl、Python、Go の標準 DNS | 選んだ実装・build・resolver ごとに A/AAAA、UDP と制御した TCP 質問、NXDOMAIN と一致する名前、外側受信0。特定実装だけ通ればその行だけ対応 | curl/Python 等の終了・独立受信・JSON を照合。システム DNS の名前が取れない行は「未観測」。統合ログの拒否回数を名前や件数に変換しない |
| IP 直指定、IPv4/IPv6 | 段階 A が使える環境で実際の IP:port。B の名との因果を推定しない。片方の family しか通らなければ明記 | 外側の到達可否と、子側の JSON が表す範囲を別欄にする。直接宛先・件数は現行 `not_observed` |
| 未対応・途中停止・大量・不正入力・同時実行 | 通知不能 Linux、:53 bind 不可、途中停止と上限、無害な異常入力でも隔離・資源制限・125の規約が保たれる | Seatbelt と named Mach 制限を維持。OS 更新で試験が再現できない行は未確認へ戻す |

D03 の出力は README 日英の「手段・到達可否・取れる名前・帰属・実測環境」の表と、再実行可能な対照手順。macOS 27.2 での curl/Python の名前欠測、mDNSResponder の制約、既存の IPC 受信側試験を起点にする。これだけで macOS のあらゆる経路を遮断できたとは判定しない。[macOS と Linux の記録](dns-attempts.md) · [macOS IPC 試験](../tests/macos-ipc.py) · [受信側の回帰試験](../tests/receivers.py)

## 7. 0.8 は「どのエージェントの、どの操作か」を追う

`agent -- COMMAND` は非隔離の親にローカル HTTPS 環境プロキシを設定し、そのプロキシに届いた CONNECT を受ける。PATH にある12個の shim は、対応コマンドを個別に記録する。`agent-env` は shim を利用するシェル用の入口。親行は同じプロキシを使う子孫を含み、透過的なプロセス別計測ではない。現行の子行は祖先のプロセス名による推定を持つ場合がある。実 Codex CLI の macOS 証拠はローカル模擬 API に対する1ターン。Claude/Cursor や有償 API の実通信へ一般化しない。[親の起動](../src/agent.rs) · [shim・履歴](../src/session.rs) · [実測範囲](../README.md#codex-本体の通信macos-実測)

**E01 のデータ契約案**。監督側が開始ごとに予測困難なローカル `session_id` を作り、操作ごとに一意な `operation_id` を採る。履歴に必要な最小値は session、operation、直属の親操作が分かる場合の `parent_operation_id`、観測範囲、帰属根拠。これらはローカル JSONL の追加欄候補で、実行 report や基準の必須キーにしない。識別子は認証情報・アクセス許可には使わず、外向きプロキシヘッダー、子の送信先、公開月報には載せない。

| 得られる根拠 | 表示と集計 |
| --- | --- |
| 親ランナーが自分のセッションを開始し、その専用プロキシで CONNECT を受信 | 「このセッションのプロキシで観測」。同じプロキシを使ったどの子孫かは unknown。操作別の値と合算して総量を作らない |
| 監督側が当該起動・専用記録経路を照合できた shim | 当該コマンドの操作行とセッションを関連付ける。コマンド名、子の理由、宛先とパッケージの推定を別々に提示 |
| 祖先名・継承環境だけ／競合・入れ子で不一致／対応外クライアント | 一致したヒントは inferred、根拠不足は unknown。セッションを自己申告しただけの子を確定扱いしない |
| 旧行、親の異常終了、記録上限、セッション外での単独 shim | 単独行または部分記録として読める。時刻・cwd・PID だけで別の親へ結合しない |

実装時は既存の親プロキシと shim 別ランナーの構造を保つ。親が持つローカル資源の所有・有効期間と、子が提示できる入力を分けて設計する。同一ユーザーの未信頼な子が再利用可能な識別子では、因果関係の証拠は「同じセッションの文脈」まで。証拠不足時はその表示に落とす。入れ子は内側を新しいセッションにし、関連付けに根拠があるときだけ外側への参照を付ける。別プロセスが同じプロキシを使った場合、観測点が重なる親行と子行を加算しない。cleanup・シグナル・子の exit、stdin の消費位置、既存プロキシの復元を回帰対象にする。

**利用者が辿る手順案**。既存の `veil-tell log --today` でセッションと終了状態を探し、追加候補の `veil-tell log --session ID` で親行と所属を確認できた子操作だけを読む。`--json` でも同じ範囲を返す。識別できない旧行は従来の期間検索で読める。既知のセッション内で受理した記録が0件の場合と、ID が履歴に存在しない場合は文言と機械出力で区別する。C02 の前に後者の終了値と照合規則を仕様化してから公開する。

**E02 の実行表**。Linux と macOS で、まず同時に2セッションを走らせ、各々に固有なローカル模擬宛先と shim 子操作を与える。次に入れ子、子の先行終了、親の中断、`NO_PROXY`、PATH 外で起動した無害な対照、ログ無効、旧 JSONL を試す。別セッションの ID 申告、失効した参照、親終了後の記録も独立ケースにする。自己申告だけで既知の親に結び付かず、部分記録または unknown として残ることを確認する。各行で親行数、子行数、相関、ユーザー側 exit、模擬先の受信、未観測表示を照合する。パイプ・端末・読み取り専用通常ファイルは実行前後の入力互換も確認する。単体の模擬 CLI 成功は実 CLI の対応欄に転記しない。[既存の end-to-end 試験](../tests/agent_env.py)

対応表は Codex・Claude Code・Cursor CLI を別行にし、各 OS で版、観測した親/子経路、実バイナリか fixture か、模擬接続先か実サービスかを併記する。初めの基準は実 Codex CLI＋模擬 API。少なくとも一つの実 CLI で「親の起動→安全な子操作→終了→履歴で照合」を両 OS で再現してから共通フローを公称する。各追加 CLI は個別にその条件を通った範囲を公称する。実アカウントや有償 API が必要な行は事前合意を取り、未実施ならそのまま記載する。

**プライバシーの受け入れ**。親はプロンプト・起動引数・鍵・TLS 本文を採取しない。既存の子履歴は既知の機密引数を伏せても自由形式の argv に機密が残り得る。新しい相関表示はコマンド名中心とし、全文 argv がなくても操作を追える設計とする。既存の履歴無効化 `VEIL_TELL_LOG=off`、日単位10 MiB・保持30日、行の切詰め、壊れた行の扱いを試験する。秘密に見立てた合成マーカーで、既定の新規項目・公開例・失敗診断への流出を確認する。npm 等の一時ログから保存するのは許可した診断語彙のみを維持する。[履歴と既知の制約](../README.md) · [失敗時の診断抽出](../src/manager_files.rs)

## 8. 1.0 の公開契約

### 8.1 保存形式と利用側

C01 は v0.6.0 を固定して、合成データで作った最小・全項目・異常の fixture、生成した版とコマンド、JSON の意味上の期待値を採る。古いバイナリでしか出ない形はそのタグから採る。C02 はそれらを期待値に使う。新 writer が出した値で旧 fixture の正解を更新して互換違反を消さない。

| インターフェース | 固定する点と扱い |
| --- | --- |
| 基準 JSON v1 | 必須は `schema_version: 1`、`coverage: "http_connect_requests"`、`backend`、`destinations`。宛先は正規 host・443・正の attempts、順序は一意に整列。lockfile・attempted・volume・宛先帰属は既存形式に従う。未知版・壊れた必須値は実行前 125。親は実行前に判定用スナップショットを読む。隔離で保護するプロジェクトの基準と Action が base から取得するコピーの保護を試す。ローカル proxy モードで任意の入力パスに書き込み防止は保証しない |
| 実行 report JSON v1 | backend/mode/isolation、coverage、child_status、run_status、destinations、および条件付き attempted/direct_attempts/volume_anomalies/comparison。欠落、空、null の意味をフィールドごとに仕様化。例として直接経路が未観測なら配列省略、観測可能で試行0なら空配列。DNS と直接経路の coverage は別。上流経由は接続成立でも connected_ip が null になり得る |
| 比較 | `created`、`compared`、`new_destinations_only`、`skipped` を別扱い。最後の二つで「消えた宛先まで比較完了」と表示しない。接続許可、トンネル成立、バイトが転送されたことを独立に表す。非遮断の量比較と切断の量を区別 |
| verify JSON v1 | 通常の report と独立。destination、timeout_seconds、verdict、reason、exit_code、phase、trials で許可・拒否・必要時の復帰を表す。各 trial は run report または準備エラー。上位の判定と子の終了を区別 |
| CLI と stdout | 既存公開コマンド・オプション・終了理由を対象にする。`--json` による run の stdout を単一の JSON としてパースできること。子の文字列と診断は分離。`log --json` は行単位。CLI ヘルプにない構想上のコマンドを現行機能として固定しない |
| 制限用 TOML と Action | ポリシー v1 の version/profile/rule、host:443、allow/deny、許可側の max_sent_bytes を回帰対象に含める。Action の公開入力は baseline、command、node-version、pr-comment、出力は report のパス。summary の文言・内部 status 出力は機械判定契約から外す。report のパスが出たこととファイルの存在は別に検査 |
| 履歴 JSONL | 旧行を新しい `log` が読めること、1行単位で処理できること、未知/部分の相関を表示できることを保証候補とする。永続の監査台帳としての完全性は約束しない。保持期間・日次上限・切詰めを仕様に含める |

機械可読の仕様は C02 で、基準・run・verify を別々に、フィールド名、型、単位、必須性、省略/null、既知 enum と未知値を読んだ時の動作まで記述し、バージョン付きの入出力例を添える。バイトの集計には成功した上流経由トンネルも含める。内部の `tunnel_established` はそのまま公開キーとして要求しない。[基準の厳格な reader](../src/baseline.rs) · [run の型](../src/report.rs) · [verify の型と判定](../src/verify.rs) · [量の比較](../src/volume.rs) · [ポリシー](../src/policy.rs)

### 8.2 互換の向きと移行

1. **旧 writer → 新 reader**。旧最小 v1、既存任意項目付き v1、マネージャー名と旧ハッシュ名の基準、相関 ID のない JSONL を各々の実 CLI 入口から読ませる。保存済みの旧 run は独立した report 利用側、旧 verify は専用の契約試験用 reader に渡し、現行 CLI にない再入力コマンドを前提にしない。旧基準と同じコマンドで新規宛先・拒否・量上限の意味と終了理由を維持する。破損 fixture の分類は現行の reader に合わせ、欠けてもよい lock 証拠と必須構造のエラーを分ける。
2. **新 writer → 旧 reader**。v0.6.0 の基準トップと endpoint は未知キー拒否。互換出力モードの v1 基準を v0.6.0 の実バイナリに渡し、読み戻しと実判定を試す。新 report の任意欄は独立した旧要約器でも試す。未知欄を無視できても、新しい coverage 値の意味を古い利用側が理解したとはみなさない。既存 v1 消費側の比較範囲・失敗判定が変わる拡張は明示選択にする。
3. **表現に新しい意味が必要な場合**。新形式は別の版・別ファイルで生成し、旧版も読める期間と移行方法をリリース時に明示する。例として段階 B 用の基準は「観測元＋正規名」、比較した backend/coverage を持つ専用の基準候補とし、v1 の既知 DNS 行を暗黙に昇格させない。詳細は D01 で経路を確認後 C01 の契約例へ追加する。入力検査→レビュー用の差分→新規パスへ原子的保存→再比較の順。中断・競合・ディスク不足・未知版でも旧基準と承認待ちの整合を守る。戻すときは保全した旧基準と旧バイナリで再比較する。
4. **1.x の約束**。公開した必須フィールドの削除・型/単位変更、既存の exit/reason の意味変更、同じモードでの暗黙の許可拡大は破壊的変更として扱う。公開 CLI の版と各ディスク形式の版は別。追加項目が旧利用側で扱えることを試験してから互換と判定する。破壊的変更は別メジャーまたは opt-in の別形式に限定する。[Semantic Versioning](https://semver.org/spec/v2.0.0.html)

### 8.3 終了理由の試験表

| モード・入力 | 期待する外側の結果 | 利用側が追加で確認するもの |
| --- | --- | --- |
| 比較成功・新規なし・子成功 | 0 | 比較状態と coverage。初回採取や非隔離観測の 0 とは区別 |
| restrict で未登録、--fail-on-unknown | 20 | unknown_destination。明示 deny はこのフラグで 20 にはならず、拒否の事実と子終了を各々確認 |
| ci または該当する fail-on-new で新しい宛先/質問 | 21 | new_destination と項目の根拠。CI が新規宛先を拒否して子が非ゼロとなった場合等は additions を残す。observe で新規 CONNECT を許可し、子が独立に非ゼロ終了しただけなら child_failed・その終了値・comparison=skipped を検証 |
| 明示的な observe 基準比較で量が異常 | 21 | volume_anomaly、blocked=false。観測した転送量 |
| ci/restrict の量上限で切断 | 22 | volume_limit_exceeded、blocked=true。上限までに実際に上流へ書けた sent_bytes を独立した模擬受信側の受信量と照合 |
| 新規拒否と量上限が同居 | ci は該当時 21、restrict の未登録拒否が優先される条件なら 20 | 量の行も読む。記録不完全・基盤失敗は優先して扱う |
| 対象自身が非ゼロ、事前失敗、計測失敗 | 通常は子の終了値を引き継ぐ。準備失敗・incomplete_capture 等は 125 | 子自身の 20/21/22/125 を全て試す。run_status.reason、child_status、report 有無を照合。前処理失敗で JSON が書かれないケースも期待値 |
| 監督対象のタイムアウト・中断 | 該当する run の timed_out は 124。SIGINT/TERM の中断は 130/143 | 対象が自発的に同じ数値で終了した時と区別。途中記録から基準を採らない |
| verify 専用 | passes=0、fails=1、inconclusive=2。事前失敗 125、中断時 130/143 を別扱い | 許可側で対象宛先の応答、拒否側で実際の拒否を確認。拒否で失敗した場合は再許可で復帰して初めて fails。対象にアクセスせず子0なら inconclusive。trial の timeout 124 と外側 2 を検証 |

C01/C02 の試験は、独立した消費側の要約器による JSON 読み取り、旧バイナリを使う基準の読み戻し、実 CLI の終了値、子の起動回数、独立した模擬受信の記録を組み合わせる。とくに旧基準の移行、基準更新後の stale 候補の拒否と、並行する accept で更新を失わないこと、基準のない CI、通知と子終了の衝突、成立した上流 CONNECT の量、JSON 欠落を fixture にする。既存のテストを起点にし、既存の期待動作と公開仕様に差があれば C02 で事前に解決する。[実行と比較](../src/lib.rs) · [受信側試験](../tests/receivers.py) · [verify 試験](../tests/verify.py)

## 9. 次の AI への作業指示と公開判断

### 9.1 開始時・引き継ぎ時

最初の実装依頼では A01 を1件選ぶ。公開タグと実際の HEAD、未コミット変更、対象ファイル、今回の権限を先に確認する。基準取得・PR 比較の両端が解決した版とその根拠を並べ、ずれを確認してから直す。変更箇所は npm テンプレート、Action とその要約器、ケースを再現する試験に絞る。機能分担は下表を使い、同じファイルを同時に編集しない。

| 役割 | 所有する作業と受け渡し |
| --- | --- |
| 司令塔・統合 | 作業 ID と先行条件、対象版、提案と実装の差、受け入れ表を持つ。複数人が触る report 型・終了判定・統合ブランチには1人の編集担当を決める。各担当から結果を受けて独立対照と照合する |
| マネージャー・Actions・運用 | P/A/M を担当。テンプレート作成者は実サンプルと期待表を渡し、別担当が利用側としてコピーから確認。運用担当は対象 PR の一覧を独立に取得し、個々の通知の正誤をメンテナーと判定 |
| OS・エージェント | D/E を担当。OS ごとの受信側記録、失敗した条件、fixture と実 CLI の区別を返す。プロセス/ネットワーク隔離を変更する人と、外側で受信を判定する人を分けられるときは分ける |
| 契約・独立検証 | C/R の fixture、旧利用側、統合前後の受け入れ表を所有。対象ブランチだけを根拠に期待値を変更しない。公開担当へ対象コミット・未確認の表・再現手順を渡す |

同時に動かせる人数が少なければ上表を順番に担当する。標準の Rust/Cargo、Node、Python、Git と既存 CI を優先する。GitHub の実レビュー対応時だけ `gh-address-comments` を使い、対象 SHA とスレッドを確認する。macOS の CLI/Seatbelt は実バイナリと受信側で検証する。UI・ドキュメント用スキルの成功を OS 観測の証拠には使わない。新しい独立作業と外部リポジトリへの導入は、その時点の AGENTS.md のモデル選択と権限に従う。

**各担当から返す最小記録**。既存の試験結果・run URL・PR 説明を利用できる。別の管理サービスは不要。下記は書式例であり、実測値は実行後に埋める。

```yaml
task: A01
revision: {base: null, candidate: null, tested_checkout: null}
environment: {os_build: null, arch: null, manager_version: null, backend: null}
case: child-exits-21-without-new-destination
expected: {child_exit: 21, run_reason: child_failed, new_destinations: 0, pr_comments: 0}
observed: null
evidence: []
status: pending
next: "比較の基準、実行 JSON、表示の期待値を照合"
```

`pending` は着手前、`pass` は指定された対照と証拠がそろった場合、`fail` は期待と実測が異なる場合、`blocked` は成立条件を満たせない場合、`unknown` は根拠が足りない場合。未対応を公表してよい行は対応表の対象外条件として明記する。受け入れ必須の行に `unknown` があればそのタスクは閉じない。再試行は別の run ID で理由を添え、前の失敗を上書きしない。

### 9.2 検証と引き戻し方

- **コード変更の入口**。ソース試験は `cargo test --locked` と `cargo build --locked --bins --examples`。OS・マネージャーを使う試験は CI 定義にある Node 配布元と Linux のテスト用 IP 条件をそろえて `tests/receivers.py`、`tests/package_managers.py`、`tests/agent_env.py`、`tests/verify.py` から該当ケースを通す。ケース単体→影響するマトリクス→同じ候補 SHA の hosted CI の順。別アーキのクロスビルドは起動・隔離試験とは別欄。[実行環境・引数の正本](../.github/workflows/test.yml)
- **互換性や通知の回帰**。基準・lock・コマンド・ツールの版を保存し、一時コピーで旧版と候補版を比較する。既存 project に損傷が出る条件ではテンプレート配布を止め、固定した前版/基準を使えるようにする。誤通知は根拠、要約器、分類のどこで生じたかを確かめる。基準を広げて試験を通さない。
- **途中の失敗**。DNS 受付やプロキシ停止、ログ欠落、Action の要約失敗、観測窓の停止日を区別する。レポート出力や保存の失敗も正常終了にしない。遮断できた証拠と記録できた証拠はそれぞれ保存する。ユーザーのディレクトリへの再実行や現用設定の削除を回復手段に使わない。
- **各版の出口**。0.6 系列は A02 と M02、0.7 は D02 と D03、0.8 は E02 の証拠を日英 README と runbook に反映する。対応を見送った環境・既知の制約・性能計測の前提も記載する。これらは目標の達成条件であり、すでに配布した v0.6.0 のタグを書き換える理由にはしない。
- **1.0 の公開**。M02 と C02 の証拠をメンテナーに渡し、対象コミットと公開 API の対応表を合意する。公開承認後、同一コミットの CI、署名タグ、3対象の配布物と SHA-256/来歴、クリーンな利用側からの install・起動・0/21/22/125 と理由を照合する。1.x の Action 別名を提供するなら `v1` と固定タグ/対象 SHA の一致を別途検証する。`v0` は 0.x 利用者の参照として扱う。問題があれば固定版への復帰手順と修正版を案内し、公開済みの固定タグ・配布物を差し替えない。[配布手順](runbook.md) · [リリース workflow](../.github/workflows/release-build.yml)

A01（Action・要約器・npm テンプレート・`tests/action_summary.py`）、M01（`scripts/monthly_rollup.py`・`tests/monthly_rollup.py`）、P01（`src/lockfile.rs` の境界試験・`tests/package_managers.py` の通常→隔離→通常往復および拒否前後再利用試験、macOS arm64 上の npm 11.19.1 / pnpm 12.4.2 実機合格）をローカル実装・検証済み。hosted CI 上での Linux（x86_64 / aarch64）マトリクス実行および `@v0` 解決実測を経て各タスク完了とし、続いて `M02`（運用対象での有効化）・`P02`（Yarn/Bun/Cargo 展開）・`A02`（マネージャー別テンプレート）・`C01`（互換 fixture 採取）へ進む。実測値と運用期間は各タスクを実行した時点で記録する。

## 10. やらないこと・止められないこと・1.0 の先

### 10.1 やらないこと（製品境界）
- **常駐の監視**
- **TLS の中身を読むこと（復号・MITM CA 導入）**
- **GUI のファイアウォール化**

これらをやると LuLu・Little Snitch・OpenSnitch と正面から競合し、「軽い・sudo なし・コマンド単位」という強みが失われる。

### 10.2 止められないこと（毎版更新・明記対象）
- IP アドレス直打ちの通信（DNS を引かないもの）
- 許可済みの送り先への、ゆっくりした少量の持ち出し
- 同じバージョンのまま中身が差し替わる攻撃（`integrity` 不一致は lockfile 差分で警告可能だが、同一内容偽装や動的変更自体は別問題）
- 実行時の特定の条件でだけ動くコード
- macOS で名前が取れない直接通信、および Linux で glibc NSS / Node hook 等を経由しない静的バイナリの直接通信（各対応表で `not_observed` 等として明示）

### 10.3 1.0 の先（将来構想）
- **ローカル蓄積による複数リポジトリ横断照合**: 鳴った送り先・パッケージ・試みの記録をローカルに貯めて、自分のリポジトリ同士で突き合わせられるようにする（外へ自動送信しない）。
- **利用者の意思による任意共有**: 共有するなら利用者が自分の意思で公開できる形（例: Git リポジトリの怪しい送り先リスト）にする。中身が透明なローカルファーストなアンチマルウェアの種として育てる。
